2. 사용자의 실제 목적과 확정 범위

웹앱의 큰 단계는 1) 평면도 추출, 2) 3D 모델링, 3) 시뮬레이션이다.
1단계의 의도는 같은 층 CAD 도면 클러스터링 → OCR/텍스트로 층·용도·층고·축척 등 파악 → 같은 층 도면과 레이어를 함께 참조한 벽·문·창·공간 추출 및 틈새 후처리 → 계단·승강기를 기준으로 층 정렬·연결이다.
현재 CAD 추출은 사용자가 이 수준에서 마무리했다. 미세한 문 오류나 작은 샤프트 생략 등 합의된 단순화를 이유로 추출 개선을 임의 재개하지 않는다.
기존 UI, 시점 이동, 색상 분류, 지표 격자, 계단·승강기 강조, 차량·사람·경로·수관·송수구 계통 도구를 유지한다.

목표는 화점을 지정하고 시간이 흐를 때 건물의 어느 공간이 얼마나 위험해질 수 있는지를 3D에서 확인하는 것이다.
현장 입력은 자연어로 받되 LLM이 사전에 허용한 변수만 바꾼다. 예: 특정 실의 가연물·마감재·문 개방 상태·발화 추정 시각.
구획별 온도, 온도의 급격한 변화, 연기 농도·분포 및 노출 시간에 관심이 있다. 소방시설 기여 비교도 목표다.
재료·실 용도 정보를 근거로 LLM이 변수의 초기값과 상·하한을 설정하고, 불확실한 조건을 무작위 조합하여 여러 번 계산하려는 구상이다.
사용자는 최선·평균·최악 결과를 선택해 보여주고, 그 결과들에서 중복되는 위험 공간을 강조하고자 한다.

가장 최근 확정된 범위:
- 풍속·풍향·풍압 효과는 제외한다.
- 물리 입력과 계산 기능은 사용 CFAST 버전의 공식 매뉴얼 지원 범위로 한정한다.
- 기온·기압·습도는 공식 입력으로 연결하는 방향이다. 당일 기상 자동 수집은 아직 구현되지 않았다.
- 백드래프트·FGI 등 비공식 별도 보완 모델은 현재 보류한다. 예전 대화의 보완 모델 제안은 현재 구현 지시가 아니다.
- LLM 입력 구성, CData 시나리오 생성, 통계 집계, 기존 3D 표시 기능은 앱 계층으로 유지한다.
- FDS로 갈아타거나 독자 물리 모델을 넣는 것이 이번 방향이 아니다.

3. 사용자 요구와 Codex 제안을 구분할 것

사용자 요구: 도면 정보 기반 변수 설정, 상·하한을 가진 불확실 조건의 몬테카를로, 대표 결과 비교, 공통 위험 공간의 3D 표시.
사용자가 동의한 이해: 분포와 변수 관계는 이 구상을 구체화하는 설정이다. 실 용도와 재료 추정의 출처는 앱이 관리한다.

다음은 검수 대상인 Codex 권고이며 상세 설계 확정/구현 완료가 아니다:
- 단순히 대표 3개 결과의 교집합만 쓰지 않고, 전체 시나리오에서 실별·시간별 위험 기준 초과 비율을 집계한다.
- 최선·최악은 정의한 평가 지표와 계산한 표본 내에서 선택한다. 표본 중 최악을 절대 최악으로 부르지 않는다.
- 평균 통계 지도와 실제 계산 한 건의 재생을 구분한다. 대표 재생은 중앙 수준에 가까운 실제 계산을 선택하는 방안을 검토한다.
- 드물어도 심각한 결과를 높은 반복 빈도만으로 가리지 않는다. 빈도와 심각도를 별도로 보인다.
- '시나리오 100개 중 95개에서 초과'를 근거 없이 '현실 위험 확률 95%'로 바꾸지 않는다.
- 같은 시각과 같은 관찰 높이/상하부층 기준으로 비교한다. 시간에 따른 위험 도달 시점과 노출 지속시간도 집계한다.
- 임계 온도·급상승 판단 시간창·연기 위험 기준·시나리오 가중치·표본 수·수렴 기준은 아직 확정하지 않았다.
- 비교용 광학밀도 문턱을 소방관 안전/진입 허용 기준으로 재사용하지 않는다.

4. CData 적용 방향과 미구현 사항

제안 흐름:
기존 건물 데이터 + OCR/용도 정보
→ 근거 자료와 LLM에 의한 허용 변수 구성
→ 범위/분포/물리 제약 검증
→ CData 기반 시나리오 생성
→ 각 입력을 원 CFAST 엔진으로 계산
→ 전체 결과의 공간·시간 통계와 대표 사례 선정
→ 기존 웹앱 3D에서 재생/비교.

CData 공식 기능 중 활용 후보:
- MHDR: 시나리오 수, 난수 시드, 작업/출력 폴더.
- MRND: 분포와 범위 등 난수 생성 정의.
- MFLD: 생성 값을 CFAST 입력 필드에 연결.
- MFIR: 화재 시계열 생성 관련 설정.
- 결과 누적·통계 및 수렴 분석.
이 명칭은 공식 지침 기준이며 설치 버전에서 실제 지원·연동을 확인해야 한다.

별도로 앱이 맡을 부분:
- 용도→대표 가연물/재료 자료 선택, 출처/단위/추정 여부 기록.
- 재료 물성 묶음과 가연물량·연소열·HRR 적분의 일관성. CData를 쓰면 자동 보장된다고 가정하지 않는다.
- 문 0/50/100%처럼 이산 상태의 확률과 묶음 조건, 복잡한 상관관계 처리.
- 입력 오류·계산 실패·착화 출력 불일치 검출. 실패를 '위험 없음'으로 집계하지 않는 처리.
- 원본 CAD 실 ID ↔ solver 구획 ↔ 시나리오 결과 매핑.
- 자연어 수정 범위 제한, 입력 확인, 결과 집계·3D 비교 UI.
- 캐시·대기열·진행 표시·필요한 추가 계산 관리.

현재 존재:
work/smokeview-demo/firemodels/cfast7/cdata.exe
work/smokeview-demo/firemodels/cfast7/Documents/CFAST_CData_Guide.pdf
현재 미완료: 이 건물 대상으로 CData 연동·시나리오 생성·일괄 실행·통계 지도 검증.
설치 파일이 있다는 사실을 CData 통합 완료로 표현하지 않는다.
CData는 개별 CFAST 계산을 가속하거나 원 엔진에 없는 화재 물리를 추가하는 도구가 아니다.

5. 현재 실행 시나리오 — 임의 변경 없이 읽을 기준선

엔진: CFAST 7.7.7, 기존 바이너리 유지.
계산100구획 / 표시156공간 / 벽개구부133개 / 수직연결36개.
표시 공간과 계산 구획은 1:1이 아니다. 합쳐 계산하는 원본 실들은 같은 계산 상태를 공유한다.
현재 표시/계산 대상 밖의 공간은 '안전'을 뜻하지 않는다. cfast-demo.json의 excluded 및 solver_members를 확인한다.
계단·승강로·램프의 기존 연결 및 3D 좌표를 유지한다.
화점: 3F_R9. 30분 표시, 5초 간격 361시점. native 입력은 실제 multifloor.in의 종료시간(1801초)을 확인한다.
일반문100%, 외부문50%, 창닫힘, 승강기문1%누설, 소화설비 미작동이라는 현 예시 가정이다. 실제 현장 상태를 확인한 값이 아니다.
환경: 실내20°C, 외부20°C, 대기압101325Pa, 상대습도50%.

최초 화재: NIST SP1021 작업대 묶음 실험 그림을 수치화한 HRR 사용. 직접 측정 CSV를 확보한 것이 아니라 도표 복원이며 대표 적용의 한계가 있다.
추가 화재: R9 내 북·남 작업대 묶음, 홀R2, A/S R8의 등록 대상. 종이 표면369°C와 점화원 존재 가정에 근거한 조건부 착화.
종이 표면 조건 충족을 전체 작업대 묶음의 지정 HRR 시작에 연결한 설계 대리모델이며, 묶음 내부 화염 전파를 예측한 것이 아니다.
추가 곡선의 초기 버너 기여 제거 등 가공·대리 가정을 검수한다. NIST가 우리 건물의 연소를 검증한 결과로 표현하지 않는다.
현 결과: 북측345초, 남측350초 첫 착화 출력; 홀과 A/S실은30분 내 미착화. 착화 출력은5초 샘플 간격이다.
대칭 배치에서 IGN/로그/HRR 불일치 진단이 있었다. 비대칭 배치로 현재 예시를 실행하고 불일치 검사를 추가했지만 엔진 문제를 수정했다는 뜻은 아니다.
문·천장으로 이어지는 연속 화염 형상, 별도의 백드래프트·FGI 모델은 미구현이다.
화염 최소 화면 크기·투과 표시·연기 움직임은 가시성 효과이며 세부 유동 예측이 아니다.

10. 추가 속도 개선 — 아직 검증되지 않은 후보

A) 엔진 내부 계측 후 최적화
확인: 로컬 소스의 DASSL은 수치 Jacobian과 dense 선형계 처리, DGEFA/DGESL 호출을 사용한다.
미확인: 이 부분이 전체 시간에서 차지하는 비율. '행렬이 주병목'이라고 확정하지 않는다.
검토 후보: 함수별 CPU 계측, 반복/실패/Jacobian 호출 횟수 측정 후 수치 라이브러리 최적화 여부 판단.
물리식을 유지하더라도 바이너리/수치연산 구현 변경이면 회귀 검증이 필요하다. 몇 배 개선을 약속할 근거는 없다.

B) 중간 결과 순차 표시
관측: 약40.06초 wall에 native 상태가 시뮬레이션305초, 약200.19초 wall에615초에 도달했다.
이는 진행 상태 관측이며40초에 앱에서 완전한5분 결과를 읽을 수 있다는 보장은 아니다. 파일 버퍼링/flush/부분 파일 검증과 UI연결을 확인해야 한다.
전체 계산 자체는 단축하지 않는다. 현재 미구현.

C) 계산 구획 통합 확대
80개·70개 등으로 줄이는 실험을 제안했으나 실행하지 않았다. 기존100구획 유지가 현재 기준이다.
같은 CFAST라도 공간 통합은 물리 입력/혼합/열전달과 공간 해상도를 바꾼다. 원 조건 동일 최적화로 포장하지 않는다.
3D 모양을 유지해도 통합된 실들이 동일 결과를 공유하는 한계를 표시해야 한다.

D) 몬테카를로 운영 구조
현재와 같은809초가100번 지속된다고 단순 가정하면 순차 약22.5시간. 실제 시나리오별 계산시간은 달라진다.
독립 계산 병렬화는 전체 처리량 개선 후보이며, 단일 계산 지연시간을 같은 비율로 줄인다고 단정하지 않는다.
사전 계산·검증 캐시·민감한 변수 우선 탐색·수렴 판단을 검토한다. 새로운 자연어 조건이 기존 범위를 벗어나면 새 계산이 필요하다.
기존 결과를 필터링할 때 조건부 표본 수/대표성이 충분한지 확인해야 한다. 가까운 사례를 새로운 정확한 CFAST 결과로 표시하지 않는다.

12. 클로드 검수에서 답해 줄 질문

1) CData의 실제 설치 버전과 공식 문서를 기준으로 제안 흐름을 구현할 수 있는가? CData가 담당할 항목과 별도 앱 전처리를 구체적으로 구분해 달라.
2) 상·하한/분포/물성 묶음/HRR/연료량/문 상태의 일관성을 어떻게 검사해야 하는가? 현재 입력과 대리 가정에 필수 수정이 있는가?
3) 최선·중앙·최악 선정과 공간별 위험 반복 비율의 정의는 타당한가? 평균·확률·미계산·실패·통합 공간을 오해하지 않는 표시 방식을 제안해 달라.
4) 현369°C 조건과 자료에서 복원한 HRR을 사용한 추가착화가 공식 기능 범위와 실험 근거에 맞게 설명되었는가? 대칭 착화 진단이 Monte Carlo 실행에 주는 영향을 검토해 달라.
5) 0.25초 설정의 개선과 하부층 OD 예외를 어떻게 해석해야 하는가? 시나리오 전반에 적용하기 전 어떤 비교가 필요한가?
6) 실제 성능 병목을 확인하려면 무엇을 계측해야 하는가? 행렬 최적화 제안이 근거 있는가? 원 물리 입력을 유지하는 개선과 공간 단순화를 구분해 달라.
7) 여러 시나리오와 자연어 상호작용에 맞는 사전 계산/추가 계산/캐시/병렬 실행 구조는 무엇인가? 검증하지 않은 응답속도 수치를 약속하지 말아 달라.
8) 최소 구현 순서와 필수 검증 항목은 무엇인가? 기존 UI와 CAD 추출은 유지하고, CData 소규모 연동 시험부터 진행하는 방안을 검토해 달라.
