3. 프로젝트의 목적

나는 화재 교관 관점에서 현장 도착 시 건축물 내부의 공간별 위험을 보고 싶다.
화점을 지정하고 발화 후 경과시간, 실 용도, 재료, 가연물, 문·창 개방 상태, 소방시설 조건 등을 바꾸었을 때 어느 층·어느 실이 언제 위험해지는지 3D로 보여주는 것이 목적이다.
예를 들어 “이 방 천장에 우레탄폼이 5cm 피복되어 있고 발화 5분 후 도착했다면 어디가 위험한가”라는 자연어를 앱이 지원하는 변수로 바꾸고 재계산하는 방향이다. 이 사례의 모든 재료·연소·피복 효과가 이미 구현됐다는 뜻은 아니다.
관심은 열과 연기 노출, 온도 수준과 급격한 상승, 체류시간, 이동 동선 및 호흡장비 사용시간, 소방시설의 기여다. 현장 판단을 돕는 공간 정보가 목표다. 이런 위험 지표·호흡장비 모델이 모두 구현됐다고 설명하지 마라.

4. 반드시 유지할 세 단계

1단계: CAD → 평면도 추출
- 같은 층에 해당하는 여러 CAD 도면을 먼저 클러스터링한다.
- CAD 문자/OCR 등으로 층, 실 용도, 높이, 축척 등의 정보를 얻는다. 이를 모든 재료 정보가 자동 확정되는 기능으로 확대하지 않는다.
- 같은 층의 여러 도면과 레이어·중첩 영역을 확인하고 틈새 보강 등 후처리를 거쳐 벽·문·창·공간을 추출한다.
- 문·창은 벽에 존재한다는 제약, 실제 공간을 가르는지, 실내/외부 연결인지 등을 활용한다. 작은 기호 하나를 무조건 문으로 인식하지 않는다.
- 층간 정렬은 계단과 승강기를 기준으로 한다. 수직 이동의 기본 종류는 계단·승강기·램프다.
- 지하주차장과 차량 진입 램프를 구분한다. 외부 창문을 통한 수직 화재 전이는 별도 고려 대상이며 이미 구현했다고 간주하지 않는다.
- 나는 “캐드 → 평면도 추출은 이쯤에서 마무리”라고 결정했다. 미세한 문 오류를 0개로 만들겠다고 이 단계를 임의로 재개하지 마라.

2단계: 기존 웹앱에서 3D 모델링
- 기존 인터페이스와 내가 공들인 기능을 보존한다. 새 별도 뷰어를 만들어 기존 기능을 누락하지 마라.
- 기존 시점·카메라 조작, 층 선택, 색상 분류, 지표면 1m 격자, 투명도, 계단·승강기 표현을 유지한다.
- 계단과 승강기는 다른 구조물보다 투명도 영향을 적게 받아 식별하기 쉬워야 한다. 과장해서 건물 외곽을 뚫고 나타나는 강조는 원하지 않는다.
- 차량·사람·진입경로·수관·송수구/소방시설 계통 도구 등 기존 기능은 먼저 실제 구현을 조사하고, 삭제나 통합은 나와 범위를 정한 뒤 진행한다.
- 구조 슬래브와 반자를 구분한다. PH 옥상 바닥과 직하층 상부 슬래브 관계를 유지한다.
- 위층 바닥과 겹치지 않는 아래층 돌출부를 검토해 테라스로 표현한다. 이중 실선이라는 이유만으로 층고만큼의 벽을 세우지 않는다. 실내 경계 벽과 외곽 난간을 구분한다.
- 기존 B1 램프는 B1↔1F 높이차 5.10m, 반원 180도 표시 해석을 적용했다. 방향과 180도는 모델 단순화이지 실측 확정값이 아니다.

3단계: CFAST 기반 계산과 위험 시각화
- 현재 엔진은 공식 CFAST 7.7.7이다. “라이트 FDS”라는 과거 명칭만 보고 FDS를 새로 도입하거나 별도 물리 엔진을 만들어서는 안 된다.
- 물리 입력·계산은 해당 버전 공식 매뉴얼 지원 범위에 한정한다. 풍속·풍향·풍압 연동은 내가 현재 범위에서 제외했다.
- 기온·기압·습도 등 지원 입력은 검토 대상이나 자동 기상 연동이 완료된 것은 아니다.
- 작은 샤프트, 반자 위 공간, 고정창/개폐창의 세밀한 구분 등 합의한 단순화를 다시 필수 결함 목록으로 요구하지 마라. 정확한 적용 범위는 기록과 코드에서 확인한다.

5. 집에서 우선 현재 결과를 띄워라

- 먼저 OS, Python, 저장소 경로, Git 상태와 필요한 파일의 존재를 확인한다.
- 저장소 루트에서 python preview.py를 실행하고 http://127.0.0.1:8831 을 연다. Windows에서 필요하면 py -3 preview.py를 쓴다. 포트가 사용 중이면 --port 8832 등으로 바꾼다.

7. 새 PC의 재현과 보존 원칙

- requirements.txt는 의존성 목록이며 깨끗한 환경에서 고정 검증한 lock 파일은 아니다. OS와 import 문제를 실제로 확인하고 필요한 범위만 고친다.
- Python 설치본, cad-deps, 모든 과거 실행물, 작업 DB, 계정/API 키는 복사하지 않았다.
- DWG 신규 처리는 별도의 LibreDWG dwg2dxf와 DLL 설치가 필요하다. DXF 표본과 혼동하지 않는다.
- 동봉 CFAST 실행 파일은 Windows용이다. 집 PC가 다른 OS라면 실행 가능성을 확인하고 별도 설치/빌드 필요를 설명한다. 엔진 버전을 조용히 바꾸지 않는다.
- 현재 시나리오의 이식 진입점은 python run_current.py --build-only다. native 계산까지 하려면 python run_current.py다. 출력은 outputs/home-run에 생성된다.
- 현재 물리 조건을 확인하는 데 처음부터 30분 전체 재계산을 할 필요는 없다. 먼저 저장 결과와 build-only 입력을 대조한다.
- work/run_cfast_current.ps1 및 과거 설치 스크립트에는 이전 PC 절대 경로가 남아 있다. 원문을 무작정 실행하지 마라.
- 이식본에서 생성된 v30 입력은 보관된 입력과 바이트 단위 일치가 확인됐다. 기준 입력 SHA256은 41eafd8d39e099903a89d84a1a006620780b0e6fb4c2dd282402690a56921644다.
- CHECKPOINT-VALIDATION.json은 입력 보존·파일 일치·HTTP 제공 검사다. 새 PC의 전체 파이프라인 검증이나 실제 화재 정확도 검증이 아니다.
- 기준 snapshot/native 결과는 덮어쓰지 말고 변경안·비교 결과를 별도 경로에 남긴다. 해당 실 ID, 층, 좌표, 건물 해시를 유지/확인한다.

8. 현재 시뮬레이션의 실제 상태

- 최신 화면 기능은 v31, 최신 적용 계산은 v30이다.
- 현재 표본은 3층 실내 화점, 30분 계산이다. 100 계산 구획, 156 표시 공간, 36 수직 연결을 사용한다. 표시 공간 모두가 독립적인 solver 구획은 아니다.
- 가연물은 화면에서 20개 단위 가구로 단순화하고 계산은 대표 화원 7개다. 격자 단위를 각각 독립 연소시키는 모델이 아니다.
- 나는 이 단위를 가로·세로·높이·재료·열량 등 향후 변수 입력을 위한 재고 단위로 사용하려 한다.
- 홀과 A/S 재고를 문 근처/안쪽 두 대표 묶음으로 각각 50% 분할했다. 총 지정 HRR·면적 곡선, 총열량 7887.644669MJ와 환산연료 435.781473kg을 보존했다. 이는 실제 건물 재고 실측값이 아니다.
- 기본 가구 표시 높이는 0.75/1.2/1.8m 등이다. 화면상 높이와 착화 표면 노출 높이를 혼동하지 않는다.
- NIST SP1021 작업대·컴퓨터·의자·서류 묶음의 HRR 곡선을 도표에서 수치화했다. 원 계측 CSV 자체가 아니며 연료 수율·연소열 등은 별도 대리 가정이 남아 있다.
- 일반문·외부문·승강기문·수직연결에는 각기 다른 개방/유효면적 가정이 있다. “문은 모두 완전히 열림”이라고 단정하지 말고 native 입력과 connection-manifest를 읽어라.
- 현재 화재실 내부 추가 착화가 있지만 다른 방의 가구는 369°C 조건을 충족하지 않아 미착화다. 조건에 맞지 않는데 화염을 강제로 생성하면 안 된다. 369°C를 모든 재료의 보편 착화온도로 설명하지 않는다.
- 345/350초는 5초 간격 출력에서 본 추가 화원 시각이다. 정확한 native 로그 시각과 구분한다.

9. 반자고는 이미 수정했다

- 과거 계산은 층간 높이 5.5m 등을 그대로 써서 반자 위 체적까지 포함했다. v30에서 도면상 3,000 표기를 확인하고 해당 실에 반영했다.
- 도면 정보 우선, 없으면 실 용도로 추정한다는 것이 내 결정이다. 미확인 일반실 3m/위생실 2.4m 등의 가정과 수직 코어/연결 높이는 구분한다.
- 건물의 구조 층고나 층간 정렬을 전부 3m로 바꾸지 않는다. 계산 반자 높이와 구조적 높이는 별개다.
- 반자 적용 후 홀 대상 표면 최고 약109.485°C, A/S 약50.1709°C로 바뀌었고 타실 미착화는 유지됐다. 상세 비교는 v30 결과를 읽는다.
- 경계 열물성은 기존 콘크리트 대리값이 남아 있으므로 실제 반자 재료까지 검증 완료했다고 설명하지 않는다.
- 연기 표시 시작에 사용한 OD 0.001/m는 표시 기준이며 현장 위험 임계값이 아니다.

10. 화염·연기·플룸 표현에서 지켜야 할 것

- 기본 모드는 계산 정보를 읽기 쉽게, 실감 모드는 시각적 표현을 풍부하게 하는 방향이다. 실감 표현은 허용하지만 실제 계산과 구별해야 한다.
- 화염이 짙은 연기에 완전히 가려져 보이지 않는 문제가 있었고 표시 우선순위를 조정했다. 기존 가시성을 퇴행시키지 않는다.
- “오징어 다리”처럼 긴 리본 불꽃은 내가 명시적으로 싫다고 했다. 재도입하지 말고 기존 화염 형태의 크기·패턴 변화 범위에서 다룬다.
- v29는 공식 CFAST 상관식의 화염 높이·플룸·천장 제트를 후처리 표현에 사용한다. 주황 화염, 보라 상승 플룸, 청록 천장 고온 가스를 구별한다. 천장 고온 가스를 무조건 불꽃으로 표시하지 않는다.
- 화면의 플룸/천장 제트 메시가 자동으로 다른 방 착화 계산에 전달되는 것은 아니다. native TARGET/열전달 계산과 후처리 표시를 코드로 구분해라.
- DJET는 구획별 개구부 연소 합계다. 문 위치에 그린 연출을 특정 문별 계산 결과라고 설명하지 않는다.
- HRR_E와 HRR 차이의 1%·1kW·10초 기준은 앱의 산소제한 표시 기준이다. NIST가 정한 보편적 “환기지배 전환 시각” 기준으로 말하지 않는다.
- native 출력과 후처리식 대조가 잘 맞았다는 사실을 실제 건물 화재 정확도 보증으로 바꾸지 않는다.

11. CData/몬테카를로와 자연어 제어의 목표 및 미구현

- 최종 의도는 도면/OCR의 실 용도·재료 정보 → 근거 기반 LLM 입력값 제안 → 상한/하한·확률분포·변수 간 관계에 따른 표본 생성 → CFAST 계산 → 3D 대표 사례·반복 위험 표시다.
- 문·창 개방은 우선 닫힘/50%/완전 개방 정도의 단순한 제어를 원한다. 실제 CFAST 입력으로 어떤 값을 바꾸는지와 누설 가정을 명시해야 한다.
- 재료와 연소열·수율·착화 기준을 물리적으로 무관한 독립 난수로 섞지 않는다. 재료 묶음, 에너지 보존, 위치/개구부 기하 조건을 함께 관리하는 방향이다.
- “최선·평균·최악” 대표 사례와 여러 조건에서 반복되는 위험 공간을 보고 싶다. 아직 위험 점수·대표 선정 기준이 최종 확정되거나 구현된 것은 아니다.
- 검수 제안의 분위수에 가까운 실제 실행 사례 선택, 관찰 높이의 온도/OD 지표, 유효 표본의 초과 비율 등은 제안과 확정 사항을 구분해라. 서로 다른 실행의 실별 최대값을 조합한 가짜 시나리오를 실제 결과처럼 재생하지 않는다.
- 표본 내 초과 비율은 설정한 입력 분포에 따른 결과다. 검증된 현실 화재 발생확률로 단정하지 않는다.
- CData 입력 생성·실행·집계·자연어 수정 UI는 아직 연결 완료되지 않았다. CData가 모든 실별·시간별 지도를 자동 완성한다고 설명하지 않는다.
- 설치 당시 background.exe가 없었고 이 체크포인트에는 CData 실행 파일도 포함하지 않았다. 공식 지침 PDF와 native CFAST는 있다. 실행환경을 다시 확인한다.

12. 검수에서 남은 문제와 성능

- Claude 검수 결론은 조건부 적합이었다. 보고서의 제안을 그대로 맹신하지 말고 현재 v30 코드, 공식 7.7.7 문서/소스와 다시 대조한다.
- 반자고 문제는 v30에서 수정했다. 연기 수율의 대리값·출처와 TABL이 CHEM 상수를 덮어쓰는 문제, 화원별 독립 변수화, 근접한 착화 표면 배치 민감도, 동시착화 불일치 문제 등은 남은 점검 대상이다.
- v30에서 대표 묶음 수를 늘렸다는 사실만으로 CData 독립 변수화가 완성됐다고 판단하지 않는다.
- 동시착화 때 IGN·로그·HRR이 불일치하는 사례가 기록되어 있다. 재현 조건과 현재 검사를 확인하고, 이런 표본을 “무효/실패”로 분류해야지 “위험 없음”으로 세지 않는다. 엔진 자체 수정이나 공식 결함 확정 여부는 별도로 확인한다.
- 과거 floor_summary의 max_*가 최댓값이 아닌 마지막 시점이라는 검수 지적도 있다. 실제 현재 코드를 확인해라.
- v27에서는 같은 당시 시나리오의 30분 실행이 34분40초 → 13분29초로 줄었다. 현재 v30 반자 적용 실행 기록은 약25분50초이고 일부 동시 실행이 있어 통제 성능 비교가 아니다.
- 동일 입력 캐시 약2.28초는 조건이 바뀔 때의 계산 성능 해결책이 아니다.
- 최대시간간격 0.25초는 기록상 효과가 있었지만 모든 시나리오에서 최적이라는 결론은 아니다. 온도 조건부 착화가 있던 기존 엔진 상한은 이미 1초였으므로 “무제한→0.25초”라고 말하지 않는다.
- v27 상부층 온도 최대차 약0.853°C, 하부층 OD 예외가 있었다. 수치차이 0이라고 말하지 않는다. 관찰 높이 기준 비교 제안은 물리 엔진 오차를 없앤다는 뜻이 아니다.
- 행렬 계산이 주병목이라는 추정은 입증되지 않았다. 함수별 계측과 통제 비교 전에 GPU나 특정 최적화의 속도 향상을 보장하지 않는다.

13. 아직 연구 단계인 항목

- 벽 없이 넓은 물류창고의 위험 구역 구분은 검토만 했다. 관찰격자와 실제 계산 구획은 다르다. 벽 없는 공간을 임의의 작은 방들로 나누고 정확해졌다고 해서는 안 된다.
- 구조 재료에 따른 열 손상/붕괴 위험도 검토만 했다. 철근콘크리트·철골·목조 구조체와 샌드위치패널 외피를 구분해야 한다. CFAST만으로 층/실 붕괴 시점·확률이 계산된다고 말하지 않는다.
- outputs/대공간-위험구역-구조손상-검토-20261015.txt를 읽고 이후 내가 요청할 때 진행한다.
- 백드래프트·FGI 등의 별도 비공식 보완 모델은 현재 공식 CFAST 범위 한정 결정으로 보류된 제안이다. 과거 대화를 이유로 임의 구현하지 않는다.

14. 이번 첫 응답과 작업 방식

먼저 기록과 실제 파일을 읽고 가능한 환경 점검·현재 결과 실행을 진행해라. 모든 것을 처음부터 다시 설명해 달라고 하지 마라.
첫 중간점검에서는 다음을 간결하고 구체적으로 정리해라.
A. 실제로 읽은 핵심 파일과 현재 기준 버전.
B. 집 PC에서 현재 모델이 열리는지, 실행 주소, 확인한 기능과 아직 확인하지 못한 기능.
C. 완료/부분 구현/미구현을 나눈 표. 저장 결과 재생과 새 계산 실행을 분리할 것.
D. 기존 UI의 유지할 것/합칠 후보/숨기거나 삭제할 후보. 바로 삭제하지 말고 실제 코드·화면을 근거로 제안할 것.
E. 검수 지적 중 해결된 것과 남은 것, 다음에 먼저 처리할 3가지 및 이유.

중간점검 요청만으로 장시간 전층 재계산, 대형 리팩터링, 새 엔진 도입을 시작하지 않는다. 실행환경의 작은 이식 문제는 기존 결과를 보존하면서 해결하고 변경을 기록한다. 막히면 오류와 필요한 최소 조치를 명확히 알려라.
나의 후속 지시가 오면 그 범위에서 끝까지 진행하되, 기존 기능·사용자 결정·계산/연출 구분을 유지해라. 한 번 정한 단순화 조건과 보류한 기능을 매번 잊고 다시 논의하지 마라.
변경 시 코드·입력·결과·비교·한계와 재현 방법을 기록하고 CHECKPOINT와 작업기준 복구 기록을 갱신해라. 대화에만 남기지 마라.
